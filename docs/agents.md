# Using hotpath from AI coding agents

hotpath has two agent-facing pieces. Both call the same CLI; neither contains a second implementation of the toolkit.

## MCP server

```
pip install .            # installs `hotpath` and `hotpath-mcp`
hotpath-mcp              # or: hotpath mcp
```

Transport is local stdio (newline-delimited JSON-RPC 2.0). Run it from the directory where your `hotpath.local.json` and `results/` live (`hotpath init` there first); file arguments must stay inside that directory.

### Client configuration

Read-only (the default; no GPU work can be started):

```json
{ "mcpServers": { "hotpath": { "command": "hotpath-mcp", "args": [] } } }
```

To let an agent run experiments, benchmarks and profiles after you agree to each one, the operator starts the server with `HOTPATH_MCP_ALLOW_ACTIVE=1`. An agent cannot turn this on itself.

- **Claude Code**: `claude mcp add hotpath -e HOTPATH_MCP_ALLOW_ACTIVE=1 -- hotpath-mcp`, or in `.mcp.json`:
  ```json
  { "mcpServers": { "hotpath": { "command": "hotpath-mcp", "args": [], "env": { "HOTPATH_MCP_ALLOW_ACTIVE": "1" } } } }
  ```
- **OpenCode 2.x** (`opencode.json` in the working directory; V2 puts servers under `mcp.servers`):
  ```json
  {
    "$schema": "https://opencode.ai/config.json",
    "mcp": { "servers": { "hotpath": { "type": "local", "command": ["hotpath-mcp"], "environment": { "HOTPATH_MCP_ALLOW_ACTIVE": "1" } } } }
  }
  ```

If the client cannot find the command, use the absolute path to `hotpath-mcp` inside your virtual environment, or `python -m hotpath mcp` with that environment's Python. Start a new session after changing the configuration.

### Active tools run as jobs

An experiment takes minutes to hours, and clients limit how long one tool call may take (public issue reports describe the Claude Code desktop app cancelling stdio calls after about 60 s and older OpenCode versions cutting tool steps at 120 s; not verified here). So an active call starts a job and returns within `wait_for_result_s` (default 45 s, at most 55): with the full result if the job finished, otherwise with its job id, progress (`launch 4 of 6, 36 of 54 requests done`) and latest output. `hotpath_job_status(job_id, wait_s=45)` waits up to 55 s per call and returns the full result once the job has finished. For clients that allow longer tool calls the operator can raise that limit with `HOTPATH_MCP_MAX_WAIT_S` (seconds, up to 3600) in the server's environment, so a long run needs fewer polls; status replies say which wait to use. For `hotpath_improve`, status also names the loop's phase (which step, its estimate, the validation) and the steps finished so far; `hotpath_job_cancel(job_id)` stops the job's whole process tree, including the `llama-server` processes it launched. One active job runs at a time (they share the GPU). Jobs belong to the MCP server process: when the client exits, running jobs are stopped. Their output files stay in `results/local/jobs/`.

### Safety model

- Active tools are **off by default**. The operator enables them by starting the server with `HOTPATH_MCP_ALLOW_ACTIVE=1`, and every active call must also pass `confirm=true`. Agents should only do so after the user agrees. A refused call says how the user enables them in Claude Code and OpenCode.
- `measure` can only target servers in `owned_servers` in your local config; the `--i-own-this-server` override is not exposed. `init` never adds your running server to `owned_servers`.
- Experiments launch their own servers on the spec's port and never touch your regular server. If your server holds the VRAM an experiment needs, the experiment fails its preconditions and names the server; hotpath never stops, restarts or reconfigures a process it did not start. Discovery recognizes hotpath's own experiment servers and never reports them as yours.
- Paths: experiment specs, workloads and records must be inside the directory the server was started in, or in a directory listed in `HOTPATH_MCP_EXTRA_ROOTS` (separated by `;` on Windows, `:` elsewhere). Models read for their header, server logs and discovery `roots` can be anywhere (read-only, never a network path; drive roots are refused); `hotpath_bench` benchmarks only the configured `model_path`. Binaries found under discovery `roots` passed by an agent are inspected statically but not executed. Runtime binaries, model paths and build directories for launches come from `hotpath.local.json`, not from tool arguments.
- Launch contents are checked against an allowlist, at the launch. Every process the MCP server starts runs with `HOTPATH_AGENT_GATE=1`, and in that mode every spec hotpath is about to launch, whoever produced it (an agent through `hotpath_experiment_run`, or the improve loop from an observed command line, `server_args`, an agent's `args` or a resumed session's saved state), is checked immediately before the launch, on the content that is launched: `binary`, `model` and `path_prepend` must be `${key}` references into your `hotpath.local.json`; every server argument of every arm's full argument list must be an allowlisted tuning setting (GPU layers, context, batch and microbatch sizes, parallel slots, flash attention, KV-cache types, cache and checkpoint sizes, threads, device split, chat-template name, reasoning format, logging verbosity, endpoints such as `--slots`/`--metrics`); environment variables must be `GGML_CUDA_*`/`GGML_SCHED_*`, a few `CUDA_*` device settings, or `LLAMA_ARG_*` mirrors of allowlisted arguments; names must be file-name safe; the workload must be inside the allowed directories. Anything else is refused, whatever it is: an allowlist, because this llama-server build alone has arguments and variables that start programs (`--mcp-servers-config`, `LLAMA_ARG_MCP_SERVERS_JSON`), enable built-in tools and a CORS proxy (`--tools`, `--agent`), reach other hosts (`--rpc`), write prompts to disk (`--log-prompts-dir`) or load a library (`GGML_BACKEND_PATH`, `CUDA_INJECTION64_PATH`), which the earlier denylist missed. `--log_file` and `--log-file` are the same argument here, as in llama.cpp. This check runs after the two authorization gates (operator flag, `confirm=true`) and does not replace them; the operator's own CLI runs are not restricted.
- An experiment never talks to a server it did not start: a port that something already listens on is refused before any launch, and after a launch the process answering on the port must be the one hotpath started. Agent-run specs keep the idle-GPU and free-port preconditions whatever they say.
- One hotpath process does GPU work at a time on this machine (a lock file in the system temp directory, naming its holder), so two agents with their own MCP servers, or a CLI run and an MCP job, cannot measure each other; `hotpath_job_status` without a job id names another process holding the GPU. An improve session can be driven by one process at a time (an exclusive session lock that recognizes a dead or recycled pid).
- A job whose MCP server is killed outright (no stdin close, so no cleanup ran) notices within seconds, stops the `llama-server` it launched and exits.
- Resume reuses a step's experiment record only when it was made from the same spec (fingerprint of arguments, environment, arms, sizes, cache mode, workload content and the configured model and binary files); a stale or mismatched record is measured again. Records are not signed, so a step record an agent forged with a matching fingerprint is not detected; it can at most choose which change gets validated. The validation that can make a change "Recommended" is never reused: the resumed process runs it again, and its record must name the configured model and build (size and content hash).
- Writes: `hotpath_propose` and `hotpath_workload` write a new file inside the working directory and never replace an existing one, and neither accepts a `*.local.json` name; both are advertised as not read-only. Result records are written to `results/local/`, whole or not at all. `hotpath_observe`, `hotpath_inspect` and `hotpath_measure` only contact loopback servers and follow no redirects. Network (UNC) paths are refused for every path argument, read-only ones included, since opening one makes Windows contact that host with the user's credentials.
- Calls with unknown, missing or wrongly typed arguments, or numbers that are not finite or out of range (a `NaN` budget), are answered with an error and the tool's argument list; every call gets a reply. Two active calls arriving together start one job. Every child process gets a closed stdin (it can never read the JSON-RPC pipe) and a timeout (300 s read-only, 7200 s for jobs by default, capped by `HOTPATH_MCP_MAX_TIMEOUT_S`); on expiry the whole process tree is killed.
- Outputs are returned to the agent as text, including local paths from tool output. Do not connect this server to a client you do not trust with that information.

### The agent workflow

When the user asks for their setup to be improved: `hotpath_improve_plan` (passive) shows the starting point, the first experiment, the free VRAM it needs and a rough duration; after the user agrees, `hotpath_improve` with `confirm=true` runs the loop as one job (poll `hotpath_job_status`). It adopts only `keep` verdicts, does not run cache-flag experiments without real-traffic reuse evidence, confirms two or more adopted changes in one paired original-vs-improved run, and ends with the launch line to apply. `args` (starting arguments when no server runs) refuses the same runner-owned and file-writing flags as agent-authored specs; `resume` (a session name) continues an interrupted run without repeating its completed experiments. The final answer to the user should separate what was measured and validated, what needs their decision, and that nothing was applied.

Step by step:

1. `hotpath_inspect`: the setup, its problems, and a ranked diagnosis of the running server with the next step. Read the confidence levels, the `known` / `hypothesis` split and "Not established by this evidence" before anything else.
2. Optionally, with agreement: `hotpath_measure` against a server listed in `owned_servers` to add client wall time, or `hotpath_bench`.
3. `hotpath_propose` with the diagnosis: a one-variable spec whose baseline is the user's real launch, and its plan (launches, requests, free VRAM needed, rough duration). Show the plan to the user.
4. If the user's own server holds the GPU, ask the user to stop it; do not look for a way to stop it.
5. With agreement: `hotpath_experiment_run` on the spec, then `hotpath_job_status` until it reports finished.
6. `hotpath_diagnose` with the experiment record: the keep/reject/inconclusive (or "faster, but outputs differ") verdict, the verified cache state of each arm, output identity, output validity and VRAM delta; then the findings that remain on the faster configuration, from which the next `hotpath_propose` builds.

## Agent skill

`skills/hotpath/SKILL.md` follows the [Agent Skills](https://agentskills.io) format (`name`, `description`, instructions in Markdown). It teaches an agent the install steps, the passive-first workflow, when to ask before active commands, how jobs work, and how to read results.

To use it, copy the `skills/hotpath` directory into your agent's skills directory: `.claude/skills/hotpath/` (Claude Code, per project) or `~/.claude/skills/hotpath/` (all projects); `.opencode/skills/hotpath/` for OpenCode.
