# Changelog

## Unreleased (0.3.0.dev0)

### Security
- Agent-run launches are checked against an allowlist instead of a denylist. This llama-server build has arguments and `LLAMA_ARG_*` variables the denylist did not list that start programs (`--mcp-servers-config`, `LLAMA_ARG_MCP_SERVERS_JSON`), enable built-in tools and a CORS proxy (`--tools`, `--agent`), reach other hosts (`--rpc`) or write prompts to disk (`--log-prompts-dir`); `GGML_BACKEND_PATH` and `CUDA_INJECTION64_PATH`, allowed by the `GGML_`/`CUDA_` prefixes, load a library. An `args_override` value could also carry a flag past the key check, and llama.cpp reads `--log_file` as `--log-file`. Only allowlisted tuning arguments and variables pass now, checked on every arm's full argument list.
- The check ran only in `hotpath_experiment_run`. `hotpath_improve` launched specs built from saved session state (`session.json`'s starting arguments and workload) and observed command lines without it. Every launch in a process the MCP server starts is now checked immediately before the launch, on the content that is launched (no window to swap the file).
- An agent spec could set the port of the user's own server and switch preconditions off, so hotpath's requests and slot erases would have reached that server. A port that is already listened on is now refused before any launch, the process answering after a launch must be the one hotpath started, and agent-run specs keep their idle-GPU and free-port preconditions.
- Spec, arm and label names with path components wrote server logs, records and profiler captures outside `results/`; names must be file-name safe. Network (UNC) paths are refused in MCP path arguments. Redirects are not followed. `--api-key`/`--hf-token` values and secret-named variables are redacted in records.
- `hotpath_workload` overwrote any existing file in the working directory; it now writes new files only, and writing tools are not advertised as read-only.

### Added
- `hotpath improve --requests CAPTURED` (MCP: `requests`): the loop on the application's own request bodies. Steps run per request class the median and the largest request; the final validation a broader set from the smallest to the largest per class, mostly requests the steps did not see. Request classes come from the capture's labels or the request shape. `--cache-mode`, `--step-requests`, `--validation-requests`.
- Fidelity probes for application requests (chat `logprobs`/`top_logprobs`, completion `n_probs`): the tokens stay in memory and only the comparison with the first arm is recorded. Probe comparisons also report how far a divergence carried. Requests that sample are not judged on identity.
- Field-by-field comparison of structured outputs (value hashes per declared schema property, with the property's kind) and decision agreement over `decision_fields` (configured, or the schema's enum/boolean/number fields as unconfirmed candidates). Output policy `decisions_equal`; `schema_valid` also requires configured decision fields to be equal.
- Per-class wall/prefill/decode ratios in verdicts; adoption refuses a request class that got slower beyond its own noise.
- Outcomes: every measured candidate is recommended (validated in a run of exactly that set), needs review, rejected or inconclusive, and the report says what to measure next when the evidence does not decide. A preliminary validation run recommends nothing.
- A machine-wide GPU lock: one hotpath process does GPU work at a time, whichever client or working directory started it; `hotpath_job_status` names another holder. MCP job children stop their `llama-server` and exit when the MCP server is killed outright.
- `HOTPATH_MCP_MAX_WAIT_S`: an operator can raise the per-call job wait for clients that allow longer tool calls; improve job status names the loop's phase.

### Fixed
- Resume reused any record whose file name matched the step, also one written for another spec; it now needs the spec's fingerprint.
- The session lock was check-then-write and trusted a bare pid; locks are exclusive files naming pid and process start time. Two active MCP calls arriving together could both start a job.
- A candidate whose own repeated outputs differ was judged identical from its first output; it is now `candidate not reproducible`.
- The different-build refusal compared the configured binary with itself; it compares the observed server's own executable and ggml/llama libraries with the configured build.
- The recommended launch could re-add flags the experiments never ran with (a draft model, a vision projector, template or grammar files); such a result needs review, and the report lists what was left out.
- A request the server rejects is a failed request of that arm, not a failed launch.
- Duration estimates for application requests assumed every request generates its full `max_tokens`, pricing a 15-minute validation at 54 minutes; they now use measured request times, else measured or observed generation lengths, and include the probe pass.
- MCP: wrongly typed arguments raised inside the tool thread and left the client without a reply; NaN or out-of-range numbers passed the budget check. A dry run of a running session rewrote spec files the running process reads. A killed record write left half a record. `--args` lost backslashes on Windows.

- `hotpath improve`: the diagnose -> propose -> experiment -> verdict loop run for the user within a budget (`--max-experiments`, `--max-minutes` checked against each step's estimate). Each step tests the top finding with an executable experiment against the configuration adopted so far (arguments and environment), with one workload throughout; a change is adopted only on a `keep` verdict; two or more adopted changes are confirmed by one paired run of the original launch against the improved one, which is the only cumulative claim. Ends with the user's own launch line with the adopted changes; nothing is applied to the user's server. `--dry-run` is passive and shows the first experiment. With no server and no log it measures a baseline on hotpath's own server first (`server_args`, `--args`, or defaults with as many layers as the GGUF header and free VRAM allow). After a refusal because the user's server held the GPU, running it again once that server is stopped starts from the server's last observation.
- MCP: `hotpath_improve_plan` (passive) and `hotpath_improve` (active job).
- Diagnosis: when no more layers fit with an f16 KV cache, candidate arms that move KV-cache memory to GPU layers, when the estimate gives at least two more: a context sized from the real traffic (twice the largest observed request, at least 4096, only when it at least halves the context; keeps the f16 cache) and an 8-bit KV cache with flash attention. Each is labelled as a two-setting change with its risks.
- Two `improve` runs started in the same second shared a session directory, so the second silently reused the first one's experiments; a new run now always gets its own directory.
- `improve` never adopts a change that limits what the server accepts (a smaller context) or a faster arm whose outputs differ; both are listed under "Needs your decision" with their measurements, and the best adoptable arm of the same step is adopted instead.
- `init` chooses the only working install with a CUDA backend when an NVIDIA GPU is present, and names the others.
- `hotpath discover`: the local setup without configuration, read-only and bounded. Running `llama-server` processes and their launch settings from the command line; loopback `/health`, `/props`, `/metrics`; installations (running, configured, `PATH`, standard locations, `--root` directories to a fixed depth, drive roots refused) with backends, sibling tools, and on Windows the imported DLLs that would not be found plus the CUDA toolkit directory that fixes them, verified with `--version`; GGUF headers with roles and VRAM fit; GPUs, driver CUDA version, profilers, logs, launch scripts. Lists where it looked and what it ran.
- `hotpath init` now discovers: it writes the running server's URL, binary, model, log and launch arguments (and `path_prepend` when a build needs it), each with its source; it lists ambiguous candidates instead of guessing (`--binary`, `--model`, `--server` choose), `--update` adds keys without changing existing ones, `--template` keeps the old placeholder file.
- `hotpath inspect`: discover + observe the running server + diagnose in one passive step, with the exact next commands and whether an experiment fits next to what runs now.
- `observe` and `measure` record the measured server's launch settings from its process command line; `observe` reads `/metrics` (aggregate prefill/decode time and prompt-cache reuse) and picks up the server's `--log-file` and model, or the model from the log's own `load_model` line.
- Diagnosis: a GPU-offload rule (log line, explicit `-ngl`, or the server's VRAM against the model's weights) with a stated memory estimate that chooses the candidate arm; `/metrics`-based phase split and cache reuse; findings ranked by the measured share of request time the change can act on, weighted by confidence; explicit `known`, `hypothesis` and `measured` fields; superseded findings; thin traffic is not read as a reuse pattern.
- The improve step: after an experiment, `diagnose` describes what remains on the candidate the verdict found faster, and `propose` builds the next spec from it.
- `propose` takes its baseline from the diagnosed server's observed command line (or `server_args` when it matches), sets the VRAM precondition from the GGUF header, and the plan states requests, free VRAM needed and a rough duration. Without a workload it writes synthetic prompts sized like the diagnosed real traffic.
- A hardware rule: BF16 matrices on a GPU below compute capability 8.0 (no BF16 tensor cores); a hypothesis until a prefill profile shows the fallback GEMM. Profile records are re-classified from their kernel names.
- MCP: `hotpath_inspect` and `hotpath_discover`; active tools run as jobs (result within 45 s, or a job id), `hotpath_job_status` with progress, `hotpath_job_cancel`; concurrent request handling; running jobs are stopped when the client exits; refusals explain how to enable active tools in Claude Code and OpenCode; unknown or missing arguments get the tool's argument list.

- Output fidelity: an untimed probe per prompt and arm with top-k log-probabilities (`probe_top_k`, default 10; asking for probabilities slows generation, so timed requests never do); per prompt `logprob-identical`, `token-identical` (with the largest log-probability shift), `diverged-near-tie` or `diverged` (first divergence, the baseline's and the candidate's margin, a top-k-only KL labelled as such); per arm `token-identical`, `numerically close, behavior differs`, `unverified differences`, `different, verified by policy` (an operator's checked `output_policy`), `invalid or regressed`, `baseline not reproducible`. Verdicts carry the class.
- `improve`: final validation of every adopted change against the original launch on a broader workload (six prompts from the smallest to the largest real request, the longest observed generation); when the combination fails and several changes were adopted, each is validated alone (largest gain first) within the budget and the first that passes is recommended; failed but faster combinations become decisions; without any passing validation the original launch stays recommended. Context-only control arms are reported as controls, not options. Adoption also requires no per-prompt wall regression beyond that prompt's noise, no extra spill into system memory, and VRAM headroom while running. Context-only control arms next to smaller-context arms and a decomposition of their effect. `--resume SESSION` (MCP: `resume`) reuses the experiments a session already recorded. A refusal before launching when the observed server ran another model or build than the configuration. The report opens with the result, the biggest bottleneck, kept/not kept with reasons, decisions, the validated measurement, apply and revert lines; `--dry-run` also prices the final validation.
- Context arms count `--parallel` slots, are not proposed for growing conversations, state what happens to a longer request (an error, or truncation with `--context-shift`), and become adoptable only under an operator's `max_request_tokens`.

### Changed
- The free-VRAM precondition of proposed experiments includes the KV cache at the arm's context size and KV types and a 512 MiB compute allowance; before, it counted only the weights, so a long-context arm could start without the memory it needs.
- Duration estimates use the model load time measured in the newest experiment instead of a fixed 30 s.
- `diagnose` takes the configuration to describe from the caller (`focus`), used by the improve loop for the configuration it adopted.
- Experiment preconditions that fail on VRAM, load or ports name the running `llama-server` processes and state that hotpath will not stop them.
- Argument overrides in the runner and in `propose` match all spellings of an argument (`-ngl`/`--gpu-layers`/`--n-gpu-layers`, `-ub`/`--ubatch-size`, ...), so exactly one value reaches the server.
- A decode-ceiling gap proposes a CUDA-graphs experiment only when the launch disables graphs, with the current state as the baseline arm; otherwise a decode profile.
- An experiment arm's full command line without `-ub` is reported as the build default, not as unknown.
- GGUF headers are read 2-3x faster (tokenizer arrays are skipped, not decoded).

### Fixed
- MCP child processes inherited the JSON-RPC stdin. On Windows, PowerShell (used for process and GPU counters) waited on it, so `hotpath_observe` against a running server hung until the 300 s timeout; a child could also read the client's messages. Every subprocess hotpath starts now gets a closed stdin. This affects 0.2.0.
- MCP job children import the same hotpath when it runs from a source checkout in another working directory.

### Validation
Windows 11, RTX 2080 SUPER, a llama.cpp-derived CUDA build, one 27B ternary GGUF; a `llama-server` started by hand with `-ngl 56` of 65 layers as the user's server. Discovery, init and inspect found and diagnosed it; the proposed `-ngl 65` experiment refused to start while that server held the VRAM; after it was stopped, three runs (CLI, Claude Code through MCP, OpenCode through MCP) measured wall time per request 5.0 → 1.4 s (small workload) and 11.3–11.8 → 3.3 s (default workload), decode 7.7–8.5 → 48.1 t/s, +796–804 MiB, no shared-memory spill; outputs identical on the small workload and diverging deterministically on one of three prompts at token 51 of 64 on the default workload. On prompts shaped like the server's observed traffic: wall 7.24 → 1.92 s per request, outputs identical 3/3, verdict keep. Details in the README and docs/agents.md.

`hotpath improve` on the same machine and model, with a user's server started by hand at `-c 49152 -ngl 40 -ub 128` and given 25 application-like requests: refused while that server held the GPU, then (server stopped) adopted an 8-bit KV cache with 57 GPU layers (keep, −58.9% wall) and `-ub 512` (keep, −5.9%), left `--cache-ram 0` (inconclusive) out, and confirmed the result in one paired run: wall 17.3 → 6.6 s per request (−61.5%), generation 3.4 → 9.0 t/s, +958 MiB, outputs identical 3/3. From nothing running: a baseline and one experiment whose 4.7% gain was correctly not adopted for lack of real-traffic reuse evidence. With the smaller-context arm added: `--ctx-size 4096 --gpu-layers 65` (sized from the largest of 25 real requests) measured 17.2 → 2.0 s per request with identical outputs and was listed for the user's decision, while the 8-bit-KV arm was adopted (−58.7%). A Claude Code session ran the loop through MCP (`hotpath_improve_plan`, `hotpath_improve`, 45 status polls); on its traffic-shaped workload both candidates changed greedy outputs, and nothing was adopted.

Fidelity and validation (later in 0.3.0.dev0), same machine and model: the earlier result above ("outputs identical 3/3") did not survive a broader validation. With top-10 probability probes and six prompts spanning the real request sizes, the 8-bit-KV + 57-layer + `-ub 512` launch (17.2 → 6.6 s per request) changes greedy outputs on 2/6 prompts at near-ties (margins 0.016 and 0.0005 nats); each change alone on 1/6; the smaller context (17.2 → 2.1 s) on 2/6. `improve` therefore recommended nothing automatically and listed every option with its numbers. From a full-offload launch with `-ub 64`, `--cache-ram 0` was validated alone (token-identical 6/6, -6%) and recommended. Agent sessions: Claude Code ran the loop from a request naming no tools; OpenCode resumed an unfinished session in a new conversation. A safety defect found there (the passive plan tool could run a pending step on resume) is fixed. A wider study (10 prompts of 91-4,090 tokens, 128 generated, full offload): `-ub 128`, 8-bit KV + flash attention and flash attention off each diverged on 3-5/10 prompts, all at near-ties (0.011-0.038 nats), at the same positions across different changes.

Real application workloads, outcomes and the agent boundary (later in 0.3.0.dev0), same machine and model, on 408 request bodies of a real application rebuilt with its own prompt builders (three request classes with JSON schemas, greedy): from the application's production launch, `improve --requests` tested the one executable finding, `--cache-ram 0` (allowed by 8% real prefix reuse in the server log), kept it on the step (−2.6%, logprob-identical) and validated it on 12 requests, 9 of them never run by the step: 4931 → 4782 ms per request (−3.0%), 12/12 requests and every class faster, logprob-identical, all enum/number output fields equal: Recommended. From a deliberately partial offload (`-ngl 40 -ub 128 -c 49152`) through Claude Code and MCP: 8-bit KV + 58 layers measured 41.1 → 17.0 s per request but diverged on 3/6 requests at near-ties and changed two numeric risk scores of one critic request: Needs review, nothing adopted. A near-tie flip under `-ub 128` changed two numeric score fields of a scoring request although 92.5% of its later tokens still lined up. Scripted real-MCP checks of the agent boundary (passive tools with planted session state, tampered resume, forbidden variables, a port another server answers on, malformed arguments, a killed MCP server, two MCP servers, cancel) all behaved as specified. Two independent reviews by another model found the issues listed under Security and Fixed.

## 0.2.0

### Added
- `hotpath diagnose`: ranked bottleneck findings from any mix of records (observation, measurement, experiment, bench, profile). Each finding carries the measurements it rests on, a confidence level (`confirmed` / `likely` / `hypothesis` / `insufficient`), why it matters, an opportunity bound where the measured shares allow one, the controlled experiment that would confirm or reject it, and the risks of the candidate change. Finished experiments get a per-arm keep / reject / inconclusive verdict.
- Passive diagnosis from a server log: `hotpath observe --log LOG` now keeps per-request timings, slot selection and reuse, and parse coverage; `diagnose` works from that alone (prefill/decode split on server time, real-traffic prefix reuse, CPU-fallback sessions, session drift, error lines, unreadable-format detection) and names the single best next measurement.
- `hotpath propose`: turns a finding into a one-variable experiment spec for the existing runner (baseline = your configuration; `${key}` references instead of paths) and prints its dry-run plan. Launches nothing; never overwrites an existing file.
- Request-shape experiments: `hotpath workload --from-requests` builds a workload from your own captured llama-server request bodies; arms change one thing with `request_override`.
- Explicit cache modes (`cold`, `warm`, `as-is`) with per-request cache state read from the server's `cache_n`. Cold uses `cache_prompt: false` on every request (slot erase alone is not trusted: a host prompt cache can restore an erased prompt). Prefill, overhead and wall-time comparisons use only requests individually verified in the comparison's state, pair prompts across arms, and are marked not comparable otherwise.
- Output checks at separate levels: valid JSON, required top-level keys, and full JSON Schema (Draft 2020-12) validation with the optional `jsonschema` package (`pip install "hotpath[schema]"`); `schema_validation: full` fails with an install hint instead of downgrading. Unenforced keywords (`format`, non-local `$ref`) are listed.
- MCP tools `hotpath_diagnose` (read-only) and `hotpath_propose`; `hotpath_workload` accepts `from_requests`. Agent Skill and docs updated; validated with Claude Code and OpenCode.
- 75 unit tests (`python -m unittest discover -s tests`).

### Changed
- Experiment verdicts are paired per prompt against within-prompt noise, state the workload size (marked preliminary below 3 prompts × 3 rounds), keep speed, output identity and validity separate, and describe the measured machine and workload only.
- Experiments trading prefix reuse for per-request overhead (`--cache-ram`, `--ctx-checkpoints`) carry a production gate based on the real traffic's reuse rate.
- MCP-launched experiments check the spec's contents: `binary`/`model`/`path_prepend` must be `${key}` references, environment overrides are limited to `GGML_`/`LLAMA_`/`CUDA_`, and server arguments that write files, change the network binding, download a model or change which model loads are refused. `hotpath propose` leaves such arguments (`--port`, `--log-file`, `--slot-save-path`, `--model`, ...) out of the baseline it copies from your config, so an experiment server cannot take over your server's port or log. `hotpath_observe` only contacts loopback servers; `*.local.json` files cannot be written by MCP tools.
- `hotpath tools` reports whether the optional validator is installed.

### Fixed
- Records no longer store generated text by default. 0.1 wrote the full generated text of every measured request to `output_text`, contradicting the documented "token ids only". Text is now opt-in (`"store_outputs": true`). Existing 0.1 result files are not rewritten; review them before sharing.
- A malformed `cache_n` crashed a run mid-way and values such as `-1` or `true` counted as reuse; missing or malformed values are now `unknown`, never cold.
- Summaries no longer crash on records without `cache_n` or timing fields.
- Schema-error paths no longer contain output keys.
- Two records of the same kind written within one second no longer overwrite each other (found when an agent ran two diagnoses back to back).
- Commands no longer abort with `UnicodeEncodeError` after writing their record when the console code page cannot encode a dash in a report.
- `pip install` works: the optional-dependencies table in the candidate's `pyproject.toml` had swallowed the classifiers list, which broke every install.

### Upgrading
`pip install --upgrade .` (or `pip install --upgrade git+https://github.com/denisanzora/hotpath`). No configuration change is required. Add `".[schema]"` for full schema validation.

### Compatibility and limits
Validated on Windows 11, Python 3.10, one NVIDIA GeForce RTX 2080 SUPER, with a llama.cpp-derived CUDA `llama-server`. Linux, macOS, other GPUs and runtimes are untested. Agent integration is validated with Claude Code and OpenCode in scripted sessions on one machine. Decision-level agreement with an application's own checks is not measured. See the README for the full list.
